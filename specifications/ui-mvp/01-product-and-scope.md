# 01. Продукт, границы MVP и решения

## 1. Назначение

Интерфейс должен за первые 20 секунд объяснить, кто покупает, что получает и зачем нужна платформа. За 5–7 минут комиссия должна увидеть связную сделку, роли сторон, движение оплаты, ограничения передачи и переход от цифрового учёта к физическим бутылкам. Показывать всё это нужно через продуктовые действия, без необходимости читать Solidity или настраивать кошелёк.

MVP в этом ТЗ — тестовая версия UI с завершённой демонстрацией и отдельной проверяемой testnet-интеграцией. Это не запуск реальной торговли. Требования к production-инфраструктуре обозначены как зависимости, а не включены в обещания демо.

**Обещание продукта:** wineries can offer wine directly to professional buyers; buyers can reserve, hold, resell eligible allocations, and request physical delivery; each operation has a visible status and a traceable record.

**Главная UX-метрика:** человек без блокчейн-опыта понимает разницу между резервом с депозитом, оплаченным количеством бутылок и запросом доставки.

## 3. Аудитории и задачи

| Аудитория | Ситуация | Требуемый результат | Что важно на первом экране |
|---|---|---|---|
| Независимая винодельня | Есть готовая партия или будущий урожай | Создать предложение, пройти проверку, видеть продажи и доступные выплаты | Следующее действие, партии, состояние проверки, фактически доступная сумма |
| Винотека, ресторан, импортёр | Закупает повторно, работает с количеством и сроками | Сравнить партии, понять цену и условия, зарезервировать, получить товар | Цена за бутылку, доступность, производство, сроки, документы |
| Оператор/проверяющий | Проверяет участника или документы партии | Принять решение с основанием и увидеть его эффект | Очередь, источник доказательств, полномочие на действие |
| Комиссия | Оценивает практичность и исполнимость продукта | Понять ценность и увидеть завершённый процесс | Демо без настройки, честная стадия, ясная связь с реальной торговлей |
| Получатель бутылки | Открыл QR-код | Прочитать происхождение и историю партии | Производитель, вино, происхождение данных; без требования кошелька |

Роль покупателя объединяет рестораны, магазины и импортёров. Подтип организации — поле профиля; отдельные кабинеты для них не нужны.

## 4. Обязательный объём P0

P0 означает требование для соответствующего gate, а не разрешение делать всё одновременно.

| Блок | DemoReady: обязательное | TestnetReady: дополнительное |
|---|---|---|
| Публичный сайт | Главная, каталог, партия, производитель, FAQ, pilot brief, legal/credits | Метки среды и фактического статуса deployment |
| Вход | Guided demo, выбор роли, reset/resume, synthetic data notice | Подключение, chain switch, роли/claims, отсутствие прав, выход |
| Каталог | 6 согласованных партий, фильтры, сортировка, shareable URL, empty/error states | Источники read-model без mock fallback |
| Покупка | Review → simulated approval/payment → Reserved/Paid; депозит и доплата | Approve → reserve/payBalance → receipt → подтверждённое чтение состояния |
| Активы покупателя | Резервы отдельно от оплаченных бутылок, сроки, действия | Реальные allocations, balances, eligibility |
| Вторичный рынок | Listing, отмена, покупка другим demo-участником, fee/royalty split | Реальные listing/approval/buy и изменение доступного количества |
| Доставка | Запрос → отгрузка → получение; отдельный сценарий проблемы | Escrow/burn/recovery по фактическим правам и API; данные логистики отдельно |
| Винодельня | Wizard партии, review, публикация оффера, production timeline, finance, deliveries | Запись контрактных полей, receipts, проверка milestone-grants |
| Operations | Проверка участника, партии, необходимые milestones/redemption decisions | Реальные разрешения каждого контракта; неподдерживаемые actions объяснены |
| Паспорт | Публичный read-only маршрут; QR; источник сведений и demo label | Реальные публичные сведения при наличии достоверного read-model |
| Качество | EN/FR, 360–1920 px, keyboard, reduced motion, сеть недоступна, копирайт | Wallet/RPC interruptions и восстановление pending-операции |

Все P0 demo-сценарии должны быть реализованы. Testnet-ready присваивается только сценариям с фактической цепочкой доказательств. Если безопасное хранилище документов или workflow API отсутствует, соответствующее действие в testnet недоступно с объяснением, а готовность ограничена: **Partial testnet coverage**. Это не повод оставлять заглушки в автономной демонстрации.

## 6. Режимы и достоверность

**DEMO.** Детерминированный симулятор, отдельные IDs, роли и локальный сценарий. Никаких wallet prompts. Шапка `Demo · Sample data`; все платежные CTA содержат `Simulate`. Локальное событие имеет `demo-event-*`, не фальшивый tx hash. Переключение роли сохраняет общую историю внутри сценария. Reset восстанавливает исходный snapshot. После открытой загрузки workflow работает без внешних RPC и API. При отсутствии интернета первый вход на удалённый сайт не обещается; для автономного показа использовать локальный preview server.

**TESTNET.** Вход через `/testnet`, явное сообщение о тестовых токенах, только разрешённая конфигурация сети/контрактов. Для нового blockchain MVP целевая сеть — Base Sepolia, chainId 84532, по [поправке совместимости chain 1.1](../../docs/chain-mvp/08-ui-compatibility-and-readiness.md); прежний Arbitrum deployment не переиспользуется. Перед записью обязательны проверенный manifest, bytecode, wiring и параметры TestEURe. Не выводить сеть из маркетинговой копии. Потеря RPC оставляет ошибку testnet. В demo можно перейти отдельной кнопкой с закрытием testnet-сессии UI; pending transaction продолжает отслеживаться отдельно.

**MAINNET.** В этой версии запись запрещена. Ошибка конфигурации не включает mainnet и не подключает demo вместо testnet. На странице нельзя писать `Live trading`, `Audited`, `Insured`, `Guaranteed` без отдельного подтверждённого основания.

Mode, роль, верификация участника, состояние lot и фактические contract capabilities — разные признаки. Маршрут `/app/operations` сам по себе не предоставляет полномочий.

## 7. Основные продуктовые решения

- Одна основная CTA на визуальный блок; вторичная помогает продолжить исследование. На главной основной CTA — демо, на партии — обзор условий/резерв.
- Публичные страницы рассказывают о вине, производителе и торговле. Контрактные адреса, hashes и abi names — в `Technical record`, а не в hero.
- Лот — партия вина. Оффер — условия первичной продажи. Allocation — резерв/оплаченная позиция конкретного покупателя. Listing — отдельное вторичное предложение. Delivery request — запрос физических бутылок. Не использовать один универсальный `status` на всё.
- Цена — за бутылку 750 ml, количество — целые бутылки. Коробки по 6 можно показывать как дополнительный перевод, не как подтверждённое контрактом ограничение.
- Комиссия по текущему primary-контракту удерживается с продавца. Экономика и округление определены в 04. Налоги, доставка, пошлины и gas не выдаются за включённые в цену.
- После депозита токенизированных бутылок у покупателя ещё нет. После полной оплаты появляется баланс. После request delivery токены в escrow; после подтверждения получения сгорают.
- Публичный QR ведёт к паспорту партии. Он не доказывает уникальность конкретной физической бутылки, защиту от подделки или принадлежность сканирующему человеку.
- Фильтр страны — eligibility предложения. Он не означает выполненную юридическую проверку импорта/экспорта или рассчитанную логистику.
- Нет искусственных оценок, отзывов, наград, инвесторов, партнёрских логотипов и «живых» toast о якобы чужих покупках.

| Логистический партнёр, география пилота | Синтетический маршрут внутри Франции | Fulfilment adapter |

При смене языка или среды сохраняются структура экранов, state machines и требования к достоверности. Нет необходимости переделывать UX с нуля.

## 9. Definition of success

Комиссия проходит демонстрацию с чистого браузера без специальной подготовки; показывает одну партию в нескольких ролях; видит реальные изменения общего demo-состояния; может открыть техническое объяснение и сразу понимает, что смоделировано. Интерфейс не содержит мёртвых CTA, противоречивых цифр, нечитабельных документов, потерянного фокуса или зависшей операции без возможности продолжить.

Визуальное качество принимается по 03 и 08: композиция, фотографии, ритм, состояния и движение. Наличие бордового цвета и округлённых карточек само по себе не удовлетворяет ТЗ.
